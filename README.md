# Media Lab tools

## Description
A platform to lend out tools from the Media Lab library, such as phones and VR headsets.

A student lends out a tool with their student number and first name. The platform checks that this combination exists in the database. A tool is either available or lent out, and it is available again when it is returned.

This is a starting point that is meant to be extended by you. There is no difference between administrators and students yet: everyone can add, change and delete tools. There are no reservations either.

## Getting started
1. Install the dependencies: `npm install`
2. Start the development server: `npm run dev`
3. Open [http://localhost:3000](http://localhost:3000)

`npm run dev` compiles the TypeScript, runs the database migrations, adds the sample students and then keeps watching your files: the TypeScript is recompiled and the server restarts when you save.

To lend out a tool, fill in one of the sample students, for example student number `41873` with first name `Emma` (see `seeds/01_students.ts` for all of them).

## Project structure
| File / folder | What it does |
| --- | --- |
| `main.ts` | The Express server and the API endpoints |
| `knexfile.ts` | The database configuration (SQLite, stored in `db/medialab.db`) |
| `migrations/` | The migrations that build the database tables, step by step |
| `seeds/` | The sample data that is put in the database (the students) |
| `public/` | The frontend: `index.html`, `style.css`, `script.ts` and the `Tool` class |
| `.github/` | The AI pull request validation (see below) |

You only edit the `.ts` files. The `.js` files next to them are generated by the TypeScript compiler and are not in git.

## API
| Method | URL | What it does |
| --- | --- | --- |
| GET | `/api/tools` | Get all tools. `lentToStudentId` is `null` when the tool is available |
| POST | `/api/tools` | Add a tool, body: `{ name, description }` |
| PATCH | `/api/tools/:id` | Change a tool, body: `{ name, description }` (both are optional) |
| DELETE | `/api/tools/:id` | Delete a tool |
| POST | `/api/tools/:id/lend` | Lend out a tool, body: `{ studentNumber, firstName }` |
| POST | `/api/tools/:id/return` | Return a tool |

Errors come back as `{ error: "..." }` with one of these status codes: `400` invalid input, `401` the student number and first name do not match, `404` the tool does not exist, `409` the tool is already lent out (or, when returning, is not lent out).

## Migrations
A migration describes one change to the database (create a table, add or rename a column, ...). Never change a migration that already ran: make a new one instead.

1. Create a new migration: `npm run migrate:make name_of_the_migration`
2. Write the change in the `up` function, and how to undo it in the `down` function.
3. Run it: `npm run migrate` (this also happens automatically in `npm run dev`).

### Migration log
Add a row for every migration, so the history of the database is readable at a glance.

| Migration | What it does |
| --- | --- |
| `20261029080000_create_students_table` | Creates the `students` table (`studentNumber`, `firstName`) |
| `20261029080100_create_tools_table` | Creates the `tools` table (`name`, `description`, `lentToStudentId`) |

## Seeds
A seed puts sample data in the database. `seeds/01_students.ts` adds 20 made-up students. Run it with `npm run seed` (this also happens automatically in `npm run dev`). It is safe to run more than once: students that already exist are skipped. To add a student, add a line to the list in the seed file.

## AI pull request validation
Every pull request is checked by an AI agent. The workflow in `.github/workflows/pr-validate.yml` sends the changes of the pull request, together with the requirements in `.github/pr-requirements.md`, to the agent. The agent answers each requirement with pass, fail or unclear, with evidence from the diff, and the workflow posts that answer as a comment on the pull request. It updates the same comment on every new push. It never merges or approves anything: the verdict is advice for the human reviewer.

**Setup (once)**
1. In GitHub, go to Settings > Secrets and variables > Actions.
2. Add the secrets `AGENT_URL` (the base URL of the agent, e.g. a DigitalOcean GenAI agent, an OpenAI-compatible `/api/v1/chat/completions` endpoint) and `AGENT_TOKEN` (its access key).
3. Optional: add the variable `AGENT_MODEL` when the endpoint needs a model name.
4. Students work in forks, so the workflow lives in this (upstream) repository and runs for their pull requests. That needs the `pull_request_target` event, and GitHub blocks that event by default in public repositories (enforced from 2 December 2026). Allow it for this workflow only: *Settings → Actions → Policies → New policy*, target the workflow `pr-validate.yml`, and keep `pull_request_target` among the permitted events. Afterwards, check *Policies → Policy insights* for blocked runs. A private repository is not affected by the default.

**Using opencode (Big Pickle) instead of a DigitalOcean agent:** set `AGENT_URL` to `https://opencode.ai/inference/openai/v1/chat/completions`, `AGENT_TOKEN` to your opencode API key and the variable `AGENT_MODEL` to `big-pickle`. The script ends the URL check on `/chat/completions`, so it is used as is. Untested: the opencode docs say free models are meant for use through opencode itself.

**Good to know**
- The requirements and the script are read from the base branch. A pull request cannot change the rules it is judged by, and the pull request that first adds these files is not checked.
- The agent also gets the branch name and the commit messages, so it can check the Git conventions of the course.
- The instructions of the agent are in `.github/agent-instructions.md`. Paste them in the *Instructions* field of the DigitalOcean agent and keep them in sync with `.github/pr-requirements.md`.
- Runs for the same pull request cancel each other: when two events arrive at once (for example a push and *ready for review*), the older run shows as canceled and the newest one posts the comment. That is normal.
- Draft pull requests are skipped. Pull requests from forks are checked too: the workflow uses `pull_request_target` and never runs the code of the pull request, it only reads the diff as text.
- Diffs over 120 000 characters are truncated, and the comment says so.
- To make a failing verdict fail the check, set `FAIL_ON_VERDICT` to `"true"` in the workflow.
